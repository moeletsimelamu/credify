# Model card — `credify-pd` 1.0.0

> **Experimental and advisory. Synthetic data only.** This model estimates a probability of default for *simulated* borrowers. It was trained on data generated by Credify's own documented process, so its metrics describe how well it recovers that simulation, **not** how it would perform on real people. It never approves or declines an application: a credit analyst or administrator records every decision, with their own reasons, and must acknowledge that the model is advisory.

| | |
|---|---|
| Model | `credify-pd` 1.0.0, L2-regularised logistic regression (`C = 0.01`) in a scikit-learn pipeline |
| Output | Probability of default within 12 months (PD), a risk band A–E, a "review carefully" flag, and an exact per-prediction explanation |
| Trained | 2026-11-25, on the 35,000-row training split; choices on the 7,500-row validation split; scored once on the 7,500-row test split |

## Intended use

- **For:** giving a human reviewer of a Credify application one more, clearly labelled, advisory signal next to the affordability assessment, in an educational simulation.
- **Not for:** any real lending, credit or eligibility decision; automated approval or decline; use on real people's data; pricing; marketing; or any setting where its synthetic origin could be mistaken for evidence about real borrowers.
- **Users:** loan officers and credit analysts in the Credify back office. Applicants never see their score.

## How it is used in Credify

1. At submission (and when review resumes after more information) the system pulls a **simulated** bureau report, assembles the features from the application's latest affordability assessment, profile and commitments, and scores it with the active model. A failure is recorded as `FAILED` with its reason and never blocks review.
2. Analysts can re-score while the application is under review. Re-scoring is blocked while a recommendation awaits a decision, so the cited evidence stays current.
3. A recommendation and a decision must cite the latest *scored* assessment if one exists. The decision records `departs_from_model`: approving an application flagged "review carefully", or declining one that is not, departs from the model.
4. Every assessment stores the model version, the exact feature snapshot, PD, band, threshold and explanation, and cannot be edited.

## Performance (test split, scored once)

| Model | ROC-AUC | PR-AUC | Brier | Log loss |
|---|---:|---:|---:|---:|
| **Logistic regression (served)** | **0.695** | **0.273** | **0.0960** | **0.332** |
| Gradient boosting (challenger) | 0.691 | 0.269 | 0.0965 | 0.334 |
| Prior-rate baseline | 0.500 | 0.117 | 0.1036 | 0.362 |
| *Ceiling: the generator's own probabilities* | *0.745* | *0.323* | *0.0924* | *0.318* |

Gradient boosting was not materially better (approved decision D4 needs +0.02 ROC-AUC and a lower Brier score), so logistic regression is served for its exact explanations. The ceiling shows how much signal the deliberately noisy simulation allows: the model recovers most of it.

**Calibration.** Expected calibration error 0.007 (validation) and 0.009 (test), so no calibration step was needed. (Had it been, Platt scaling would be folded into the coefficients, keeping the model a plain logistic regression.) Mean predicted PD on test 11.67 % against an observed 11.73 %.

**Operating threshold: 0.13.** Chosen on validation as the highest recall on defaulters with at most 30 % of applications flagged for careful review (a policy assumption about reviewer workload). On test: 28.7 % flagged, 54.1 % of defaulters found, precision 22.1 % (476 true positives, 1,679 false positives, 404 false negatives, 4,941 true negatives). Being flagged means *review carefully*, nothing more.

**Risk bands** (finalised on validation from the provisional table; D starts at the threshold):

| Band | PD | Share (test) | Default rate (test) | Guidance |
|---|---|---:|---:|---|
| A | < 4 % | 5.0 % | 2.9 % | Low modelled risk |
| B | 4–7 % | 26.7 % | 6.0 % | Below-average modelled risk |
| C | 7–13 % | 39.6 % | 9.2 % | Average modelled risk |
| D | 13–25 % | 21.4 % | 17.4 % | Elevated modelled risk — review carefully |
| E | ≥ 25 % | 7.4 % | 35.7 % | High modelled risk — review carefully |

**Learned versus true effects.** 17 of 18 effects have the direction the generating process intended. The exception, loan-to-income, is strongly correlated with debt-to-income and residual income, which absorb its signal.

## Explanations

For logistic regression the explanation is exact: each feature's contribution is `coefficient × (transformed value − training mean)` in log-odds, summed over the feature's columns, and the base log-odds (an average applicant, PD ≈ 10 %) plus all contributions equals the model's log-odds. The API checks this on every prediction and records a failure if it does not hold. Reviewers see the top factors increasing and decreasing risk in plain language, e.g. "Residual income 24,922.67 — decreases risk (−0.25 log-odds)", with the caveat that contributions describe the model, not the causes of default.

## Fairness (test split; audit-only synthetic attributes)

The generator deliberately gives the synthetic female group about 12 % lower income and makes income and employment depend on age, so the evaluation has something real to find. `sex` and `age_band` are never features.

| Attribute | Disparate impact (four-fifths heuristic) | Equal-opportunity difference | FPR difference | Worst within-group calibration gap |
|---|---:|---:|---:|---:|
| Sex | 0.988 | 0.012 | 0.010 | 0.003 |
| Age band | 0.873 | 0.167 | 0.083 | 0.028 |

- By sex the outcomes are close: loans scale with income, so the income gap barely moves debt-to-income.
- By age the youngest (18–24) and oldest (65+) groups are flagged more often (36 % and 35 % against 27–29 %). The ratio passes the heuristic at the chosen threshold but would fail at 0.10.
- Income and employment type act as proxies for age band. Neutralising them *lowered* the age ratio (0.842) and cost accuracy, so the model keeps them, and reviewers are told about the disparity.
- Group-specific thresholds would need the protected attribute at decision time, which Credify never uses.

The four-fifths rule is a heuristic, not a legal test. See the [fairness report](ml/reports/credify-pd-1.0.0/fairness.md).

## Safety and governance

- **Registry:** `python -m credify_ml.register` records a `CANDIDATE`; only an administrator can activate it (`POST /api/v1/models/{id}/activate`, audited), which retires the previous version. There is no upload endpoint.
- **Loading:** the API loads model files only from its read-only model directory, only after their bytes match the SHA-256 recorded at registration, and only if they were trained with the scikit-learn version it runs. Readiness (`/health/ready`) re-hashes the active model's file on every probe.
- **Inputs:** the feature builder rejects out-of-range or non-finite values; protected and proxy attributes have no field at all.

## Limitations

- Synthetic data reflects the generator's assumptions, including the biases written into it. Real borrowers would differ.
- Missed payments and months since delinquency come from a **simulated** bureau (deterministic per applicant), standing in for a real bureau report obtained with consent.
- Every synthetic loan was priced as one product (`PERSONAL_UNSECURED`); behaviour on other products is untested.
- No temporal validation, drift monitoring or reject inference: real lenders only observe outcomes for loans they approved.
- The threshold and bands encode a workload assumption (≤ 30 % flagged) that a real lender would set as policy.

## Reproducing

From `ml/`: `uv run python -m credify_ml.generate`, then `train --check`, `evaluate --check` and `fairness --check`. CI runs all four on every push; each fails if a metric moves by more than 0.0001. Field definitions are in [DATA_DICTIONARY.md](DATA_DICTIONARY.md).
